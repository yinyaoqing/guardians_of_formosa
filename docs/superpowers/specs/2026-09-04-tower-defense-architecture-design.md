# Guardians of Formosa — 技術架構設計規格

- 日期：2026-09-04
- 狀態：已確認，待轉為實作計畫
- 類型：塔防（參考 Kingdom Rush 系列的系統規格）

## 1. 專案約束

這些約束是所有架構決策的前提，任何後續變更都必須回頭檢視本節。

| 約束 | 內容 | 對架構的影響 |
|---|---|---|
| 團隊 | 單人開發，搭配 AI 協作 | 可測試性優先於開發便利性；AI 必須能自我驗證 |
| 預算 | 零成本優先 | 引擎與外掛必須免費、無營收抽成；付費資產與工具一律排除 |
| 商業模式 | 純單機買斷制 | **不需要任何後端服務**、帳號系統、伺服器驗證 |
| 平台 | 手機（iOS / Android）+ PC（Steam），未來含 Steam Deck | 需要輸入抽象層與跨比例 UI 適配 |
| 美術 | AI 生成 2D 手繪，風格需明確區隔於 Kingdom Rush，細節待定 | 資產與邏輯必須徹底解耦、視覺層可替換 |
| 首個里程碑 | 可玩 Demo，暫不上架 | 先做垂直切片，上架相關成本延後決策 |

### 已知的不可避免成本（延後至 M4 決策）

- Steam Direct：US$100 / 款（銷售達標後可退）
- Apple Developer：US$99 / 年，且必須有 macOS 機器
- Google Play：US$25 一次性

### 合規注意事項

Valve 自 2024 年起要求上架時揭露 AI 生成內容。本專案美術為 AI 生成，需納入 M4 的上架準備。

## 2. 技術選型：Godot 4 + GDScript

### 決策

採用 **Godot 4.x + GDScript**。

### 理由

1. **成本**：MIT 授權，永久免費、零營收抽成、無席次費、無強制啟動畫面。是唯一完全滿足零成本硬約束的選項。
2. **契合度**：Godot 是原生 2D 引擎而非 3D 引擎跑 2D，Node2D / TileMap / AnimationPlayer 直接對應塔防需求。
3. **迭代速度**：編輯器輕量、啟動快，單人開發最需要的就是短迴圈。
4. **多平台**：Windows / macOS / Linux / Android / iOS 全支援；Steam 端可用 GodotSteam（MIT，Godot 4 支援 GDExtension 掛載，不需自行重編引擎）。

### 已評估並排除的選項

- **Unity 6 + C#**：實務上對本專案等同免費（Personal 版年營收 US$200K 以下），生態與手機工具鏈最成熟，LLM 訓練資料量大。排除原因為：授權條款掌握在第三方手上構成長期政治風險；編輯器肥大、單人迭代慢；Git 管理成本高。對單人零成本專案屬過度配備。
- **TypeScript + Phaser/PixiJS + Capacitor + Tauri**：AI 協作最順、熱重載最快。排除原因為效能天花板——手機端跑在 WebView 中，Kingdom Rush 等級的同屏單位量（100+ 敵人與投射物特效）在中低階 Android 上難以維持幀率，且缺乏底層最佳化手段。

### 已知風險與對策

| 風險 | 對策 |
|---|---|
| LLM 訓練資料中 Godot 3 程式碼多於 Godot 4，AI 易產出 3.x 語法 | 鎖定引擎版本；在 CLAUDE.md 明令只用 4.x API，禁用 `KinematicBody2D`、`yield` 等舊寫法 |
| 現成資產與外掛生態小於 Unity | 美術本為自產，影響有限 |
| Godot 的 C# 版本在 iOS / Web 支援較弱 | 一律使用 GDScript，不引入 C# |

## 3. 分層架構

### 核心原則：模擬層與表現層分離

戰鬥邏輯寫成**不依賴 SceneTree 的純 GDScript 類別**（`RefCounted`）。Node2D 僅負責將模擬結果視覺化。

**決定性理由**：純邏輯可在不啟動引擎的情況下被單元測試。AI 協作的最大失效模式是「宣稱完成但未驗證」；當傷害計算、目標選擇、波次時序、經濟系統皆可被測試直接驗證時，AI 便能自行證明未破壞既有行為。

**附帶效益**：

- 固定步長 tick（30Hz）+ 渲染插值 → 暫停與 2x / 4x 加速僅是「本幀執行幾個 tick」，而非將 `delta` 乘上倍率（後者必然產生數值錯誤）
- 手機掉幀時邏輯不隨之變慢，戰鬥結果在不同效能裝置上一致
- 離線平衡模擬、戰鬥回放、自動化測試皆為免費附帶能力

**成本**：需額外撰寫一層 view 同步的膠水程式碼。此成本已評估並接受。

### 目錄結構

```
res://
├── core/           # 純邏輯層：不 import 任何 Node，可直接 new 出來測
│   ├── sim/        # BattleSim 主迴圈、tick 排程、世界狀態
│   ├── entities/   # Enemy / Tower / Projectile / Hero 的邏輯狀態
│   ├── systems/    # 目標選擇、傷害結算、狀態效果、波次、經濟
│   └── spatial/    # 均勻網格空間分割
├── data/           # 資料驅動定義（JSON）
│   ├── enemies/ towers/ heroes/ status_effects/ levels/
├── game/           # 表現層：只讀 core 的狀態
│   ├── views/      # EnemyView / TowerView / ProjectileView（含插值）
│   ├── fx/         # 特效與物件池
│   ├── level/      # 關卡場景、Path2D 路徑、TileMap
│   └── assets/     # 已裁切壓縮、實際進遊戲的圖集與音效（走 Git LFS）
├── ui/             # HUD、環形建塔選單、升級面板、選單
├── input/          # 輸入抽象層：原始事件 → GameIntent
├── platform/       # 存檔 / 成就 / 雲存檔介面 + 各平台實作
├── tests/          # GdUnit4，只測 core/ 與資料完整性
└── addons/         # 第三方（GodotSteam，M4 才引入）
```

### 依賴方向

單向：`game/`、`ui/`、`input/` 可讀 `core/`；**`core/` 永不 import 上述任何一層**。此規則一旦破壞，可測試性即喪失，故列為 CLAUDE.md 硬規則。

## 4. 戰鬥核心子系統

### 4.1 路徑：烘焙式路點，不做尋路

敵人走固定路徑，**不需要 A\* 或 NavMesh**。以 `Path2D` 在編輯器繪製，載入時將 `Curve2D` 等距取樣為點陣列；敵人僅持有 `distance_along`（沿路徑已行進距離）。

- 「誰走在最前面」退化為單純的數值比較 → 塔的 First / Last 目標策略為 O(1)
- 分岔路徑即多條 Path，生成時指定
- 飛行單位不吃路徑，走起點至終點直線

**攔截機制**（士兵擋路）不是動態尋路，而是敵人身上的 `blocked_by` 欄位：被攔截時停止推進 `distance_along` 並進入近戰狀態。

### 4.2 目標選擇：均勻網格空間分割

100+ 敵人配 20+ 座塔，逐幀暴力比對為 O(n²)，手機無法承受。以固定格子（約 64px）索引敵人，塔僅查詢射程覆蓋的格子。每 tick 重建索引（較增量維護更簡單且效能足夠）。

### 4.3 傷害與狀態效果

此處為塔防技術債的主要生成地，故明訂規則：

- 傷害類型（物理 / 魔法 / 真實）對應護甲與魔抗，**結算順序固定且僅有一處實作**
- 狀態效果（減速 / 暈眩 / 中毒 DoT / 破甲）皆為資料定義的 `StatusEffect`，由 `StatusSystem` 統一 tick
- 堆疊規則：**同來源刷新持續時間；不同來源取效果最強者**
- **禁止任何塔的程式碼自行計算傷害**，一律送入 `DamageSystem`

### 4.4 投射物與物件池

三種攻擊型態：即時命中（hitscan）、飛行投射物（追蹤或預判落點）、範圍傷害。全部走物件池，**戰鬥迴圈中不做任何新物件配置**——GDScript 的 GC 在手機上觸發回收會造成可見頓挫。

### 4.5 波次系統

`WaveDef` 為一串 `SpawnGroup { enemy_id, count, interval, delay, path_id }`。提前召喚下一波（獎勵金機制）即將下一波計時器歸零，不需特例邏輯。

### 4.6 效能預算

| 項目 | 目標 |
|---|---|
| 手機幀率 | 中階 Android 穩定 **60fps** |
| 同屏動態單位 | 150（敵人 + 投射物 + 特效） |
| 邏輯 tick | 30Hz，渲染 60fps 插值 |
| Draw call | < 100（精靈全部進 Sprite Atlas 合批） |

### 4.7 動畫方案：逐格 sprite sheet

**採用逐格動畫，不使用 Skeleton2D 骨骼動畫。**

理由：AI 生成的 2D 手繪角色若要綁骨，需拆成透視一致的獨立分件（頭、上臂、下臂、武器），AI 產出成功率低且修圖成本高；逐格則可用 AI 生成關鍵幀再補間。

代價為記憶體佔用。故訂定規格上限：

- 單一敵人貼圖不超過 **128×128**
- 單一動作幀數壓在 **6–8 幀**
- **記憶體佔用必須在 M2 實機驗證**，不得等內容量產完才測

## 5. 資料驅動層

### 5.1 格式：JSON（非 .tres）

違反 Godot 慣例，但針對「單人 + AI」情境的正確選擇：

- AI 能可靠地批次編輯 JSON；`.tres` 的 `ext_resource` id 引用機制易產生無效引用，且錯誤通常在執行期才顯現
- git diff 乾淨，調整數值後可一眼辨識變更
- schema 可用測試驗證（見 5.3）

**代價**：失去 Godot Inspector 的拖放編輯與型別提示。已評估並接受。

### 5.2 資料結構

```
data/
├── enemies/*.json      # 血量、速度、護甲、魔抗、賞金、貼圖路徑、動畫幀數
├── towers/*.json       # 每級的傷害、射速、射程、造價、賣價、特殊效果
├── heroes/*.json       # 技能樹、冷卻、成長曲線
├── status_effects/*.json
└── levels/
    └── level_01/
        ├── waves.json  # 波次 timeline
        └── meta.json   # 起始金幣、生命、星等目標、可用塔種
```

**關卡的切分點**：視覺與路徑留在 Godot 場景（Path2D 手繪、TileMap 鋪設）；數值與波次走 JSON。兩者以 level id 綁定。依據是路徑為空間性資料，用編輯器繪製最快；波次為時序性資料，用文字編輯最快。

實體之間**一律以字串 id 互相引用**（如 `"enemy_id": "orc_grunt"`），不存直接物件引用。

### 5.3 資料完整性測試

`tests/test_data_integrity.gd` 掃描所有 JSON，驗證：

- 必填欄位存在且型別正確
- 所有 id 引用指向存在的實體（波次引用的 `enemy_id`、塔引用的 `status_effect_id` 等）
- 所有貼圖與場景路徑確實存在於磁碟
- 數值落在合理範圍（射程 > 0、造價 >= 0、升級成本遞增）

**設計意義**：AI 修改數值後，執行測試即可確認未破壞資料，無須人工玩到該關卡才發現問題。此防線在 AI 協作下投報率極高。

### 5.4 離線平衡模擬

因戰鬥邏輯為純 GDScript 且不依賴 SceneTree，可撰寫 headless 腳本，以固定防禦佈局將關卡執行 1000 次，統計通關率與剩餘生命。調整數值時直接檢視統計結果，不需人工試玩。

在無測試團隊、AI 亦無法代為試玩的前提下，此能力接近必需品。

### 5.5 多語系

自第一天起使用 Godot 內建翻譯機制。UI 與資料中**只存 key 不存字面文字**（如 `"name_key": "enemy.orc_grunt.name"`），翻譯置於獨立 CSV。

理由：Steam 主要客群不在繁體中文市場，而事後從散落各處的硬編碼字串回頭抽取的成本，遠高於一開始即用 key。

## 6. 輸入抽象與 UI 適配

### 6.1 GameIntent

`input/` 層唯一職責為將原始事件翻譯成裝置無關的意圖。戰鬥核心**只認得意圖，不認得滑鼠或手指**：

```
BuildTower(slot_id, tower_id)   UpgradeTower(tower_id, path)   SellTower(tower_id)
CastSpell(spell_id, world_pos)  MoveHeroTo(world_pos)          UseHeroSkill(index)
SetGameSpeed(x)                 TogglePause()                  CallNextWave()
```

新增手把支援時只需增加一個翻譯器，**完全不動遊戲邏輯**。回放與自動化測試亦為附帶能力——將一串 intent 灌入模擬層即可重現整場戰鬥。

### 6.2 三套輸入設定檔

| 操作 | 觸控 | 滑鼠鍵盤 | 手把 / Steam Deck |
|---|---|---|---|
| 選建塔點 | 點擊 → 環形選單 | 點擊 → 同一環形選單 | D-pad 於建塔點間跳選 |
| 查看資訊 | 長按 | hover tooltip | 選中即顯示 |
| 取消 | 點空白處 | 右鍵 / Esc | B 鍵 |
| 施法 | 點技能 → 點目標 | 快捷鍵 + 點目標 | 肩鍵 + 類比搖桿瞄準 |
| 加速 / 暫停 | HUD 按鈕 | 空白鍵 / 數字鍵 | Start / 十字鍵 |

手把為唯一需特別設計者：自由浮動游標在塔防中手感不佳，正確解法是**於離散的建塔點之間跳選**。英雄移動與施法才需類比瞄準。

環形建塔選單在滑鼠上同樣適用，故**只需維護一套 UI 樹**。

**手把支援的處理方式**：intent 層現在就預留，實作延後至 M4。預留成本接近零，事後補則被迫回頭改 UI。

### 6.3 關卡設計約束：整幅入鏡

**所有關卡必須在最窄的目標比例下完整放進畫面，不需平移鏡頭。**

此約束省掉一整類問題：不需鏡頭平移與縮放的觸控手勢、不需處理「拖曳畫面」與「拖曳英雄」的手勢衝突、不需小地圖、手把不需移動視角。

代價為關卡空間規模有上限，路徑長度須靠繞行而非延伸取得。此為該類型的成熟做法，非妥協。

### 6.4 畫面比例與安全區

- 使用 `canvas_items` 拉伸模式配 `expand`；定義 **16:9 核心遊玩區**保證可見，更寬螢幕（20:9 手機、21:9 PC）見到的是額外邊緣裝飾，不影響玩法
- HUD 錨定於 `DisplayServer.get_display_safe_area()` 之內，避開瀏海與 home indicator
- **觸控目標尺寸統一以 >=44pt 設計，PC 上不縮小**。維護兩套尺寸的成本大於 PC 上按鈕稍大的美感損失
- 偵測到輸入裝置切換時即時替換按鍵提示圖示（Steam Deck 上玩家會插拔鍵盤）

## 7. 平台服務與存檔

### 7.1 平台服務層

`platform/` 定義介面，遊戲程式碼只與介面對話：

```
PlatformServices
  ├─ save(slot, data) / load(slot)
  ├─ unlock_achievement(id)
  └─ sync_cloud()
```

Demo 階段只實作 `LocalPlatform`（存本地、成就寫 log），**不引入任何第三方相依**。日後 `SteamPlatform`（GodotSteam）與 `MobilePlatform`（Google Play Games / Game Center）為新增檔案，非改動既有邏輯。

成就 id 自第一天起定義於資料中，避免事後回頭補埋點。

### 7.2 存檔設計

**存檔內容限定於關卡外的進度**：已解鎖關卡、星等、天賦點分配、已解鎖英雄、設定。

**明確不做關卡中途存檔。** 此決定省掉「序列化完整戰鬥世界狀態並保證跨版本可還原」，為本專案最昂貴的功能之一。

實作要點：

- JSON + `version` 欄位 + 明確 migration 鏈（v1→v2→v3），每次變更 schema 即補一段轉換
- **原子寫入**：先寫暫存檔再 rename。手機隨時可能被系統終止，直接覆寫會產生半截存檔
- 置於 `user://`。Steam 雲存檔僅需於後台設定指向該目錄，**無須撰寫程式碼**
- **不做防作弊**。單機買斷制下玩家修改自身存檔不損及他人，加密只增加自身除錯難度

## 8. 測試與版控

### 8.1 測試策略

| 測試對象 | 方式 |
|---|---|
| 核心邏輯（傷害、目標選擇、狀態、波次、經濟） | GdUnit4 單元測試，不啟動引擎 |
| 資料完整性 | 掃描 JSON 的整合測試（見 5.3） |
| 數值平衡 | headless 批次模擬，統計通關率 |
| UI / 畫面 | **不做自動化**，人工驗收 |

CI 使用 GitHub Actions 免費額度，每次 push 執行 headless 測試。UI 自動化測試對單人專案投報率過低，明確排除。

### 8.2 版控與資產管線

GitHub 的 Git LFS 免費額度為 1GB 儲存 + 1GB/月流量，**AI 生成的原始美術素材必然超出**（未壓縮生成圖動輒數 MB，且會反覆迭代）。

故切分兩層：

- `art_src/` — AI 生成原始檔、PSD、中間素材。**不進 git**，以本地 + 雲端硬碟備份
- `game/assets/` — 已裁切壓縮、實際進遊戲的圖集。進 git 並走 LFS；因規格壓在 128×128 等級，體積小，不觸及額度

`.gitattributes` 與 `.gitignore` 必須在首次提交美術資產前設好；事後自 git 歷史清除 LFS 檔案成本極高。
