## 1. 範圍

到 B3b 為止，玩家可以蓋塔、升級、賣出，敵人會沿路徑走過來被打死。但**沒有一局的概念**——敵人永遠一隻一隻冒出來，既贏不了也輸不掉。B4 把沙盒變成一局遊戲。

### 1.1 B4 做什麼

- 波次資料與 `WaveSystem`，**敵人生成移進 tick**
- 提前呼叫下一波，換取剩餘倒數折算的銀
- 通關判定與模態結算面板，含「再來一次」
- `lives` 改名並改變語意為**待撤離的平民**
- HUD 加上波次進度、下一波倒數、呼叫按鈕
- 貨幣顯示正名為「銀」

### 1.2 不在 B4 範圍

平民作為路徑上可見的中立單位、聚落建物與 ★★★、駐守單位（柵欄）、路徑陷阱、地面 DoT、新敵種、Boss、英雄、法術、潮汐與多路徑、長按查看資訊。

## 2. 這一關沒有「輸」

第一章設計規格 §0.2 決定三：

> 熱蘭遮城必定陷落，這是史實。但**不採用強制失敗關卡**——那既挫折又暗示玩家該替 VOC 惋惜。改以星等承載歷史：**撐過波次即通關**，星等取決於平民撤離人數與聚落存活數。

所以 B4 **沒有失敗畫面**。撐過所有波次就是通關；差別在救到多少人。

現有的 `lives = 20`（漏一隻扣一點、歸零就輸）直接牴觸這條決定，因此改名並改變語意。

### 2.1 `lives` → `civilians_remaining`

它現在是**待撤離的平民數**：漏過去一隻敵人，就少救一個人。歸零不是失敗，只是一個都沒救到。

**名字必須改。** 留著 `lives` 會主動誤導——下一個讀到它的人會假設歸零即失敗，而那正是規格明文排除的。JSON 的 `starting_lives` 一併改為 `starting_civilians`。

**歸零之後夾在 0，不變成負數，也不觸發任何事。** 玩家繼續打完剩下的波次，結算時救到 0 人、拿一顆星。這不是失敗狀態，只是最差的通關。

### 2.2 平民在 B4 只是一個計數

第一章規格說平民是「沿路徑移動的中立單位，敵人會攻擊他們，玩家的塔可以保護他們」。**那需要「單位攻擊單位」的機制，而現在 `MovementSystem` 裡一行攻擊邏輯都沒有**——敵人不攻擊任何東西。

那套機制正是駐守單位（柵欄）里程碑要建的。兩邊共用同一套東西，所以平民的可見單位形態跟著駐守單位一起做，B4 只做計數這個化約形態。**規格記下這是化約，不是最終設計。**

### 2.3 星等

| 星 | 條件 | B4 |
|---|---|---|
| ★ | 撐過所有波次 | ✅ |
| ★★ | 平民撤離數 ≥ 門檻 | ✅ 門檻為 `meta.json` 的 `star_civilian_threshold`（暫定 14，即 20 人中救到七成） |
| ★★★ | 未失去任何一座聚落建物 | ❌ 聚落建物還不存在 |

★★★ 等聚落進來時補。結算面板要能顯示三顆的位置，第三顆恆為未達成。

## 3. 生成移進 tick

### 3.1 現況與問題

`battle_scene._process` 自己扣計時器、自己呼叫 `_registry.make_enemy()`。B3a 已經因此踩過一次——生成跑在渲染 delta 上，暫停與倍速對它無效——當時的修法是把計時器改吃模擬時間，但生成本身仍在場景裡。

### 3.2 靠注入資料，不是注入 registry

`WaveSystem` 住在 `core/`，在 tick 裡跑，所以不能持有場景層的東西。

沿用既有模式：`WorldState.configure_for_level` 已經注入 `tower_defs` 與 `effect_defs`，再加一個 `enemy_defs`。`WaveSystem` 從 def 造敵人，與 `BuildSystem` 從 `tower_defs` 造塔是同一個形狀。

### 3.3 造敵人的邏輯只能有一份

`DataRegistry.make_enemy` 已經有一份。再寫一份就是第二個事實來源——與 B3b 的退款是同一類問題。

但這次**不必接受重複**：兩者都在 `core/`，沒有分層守衛擋著。抽成一個共用的靜態建構函式，`make_enemy` 改為呼叫它。

### 3.4 `_tick()` 的位置

現有順序是：套用意圖 → 狀態效果 → 移動 → 收集漏過 → 重建網格 → 投射物 → 塔 → 移除死亡。

`WaveSystem.tick` 插在**套用意圖之後、狀態效果之前**（第 2 步）。理由與「這一 tick 蓋好的塔這一 tick 就能開火」一致：這一 tick 呼叫的下一波，這一 tick 就生得出來，而且新生的敵人會被同一 tick 的網格重建看見、被塔鎖定。

通關判定插在**最後**，移除死亡之後——「場上沒有活著的敵人」要在死亡結算完才問得準。

## 4. 波次資料

`data/levels/level_01/waves.json`：

```json
{
  "call_bonus_per_second": 2,
  "waves": [
    {
      "delay": 12.0,
      "groups": [
        {"enemy_id": "orc_grunt", "count": 5, "interval": 1.2, "path_id": "main", "start_delay": 0.0}
      ]
    }
  ]
}
```

- `delay` — **前一波生成完畢**之後到這一波開始的秒數。第一波的 `delay` 是開局的準備時間。以「生成完畢」而非「打完」為基準，倒數的語意才單純可測，不會跟「上一波還沒清乾淨」糾纏。
- `groups` — 一波裡可以有多個群組，各自有 `start_delay` 以錯開。
- `path_id` — 目前只有 `main`。潮汐要開第二條水道時用得上，而欄位現在放不花成本。

**波次內容是暫定的**，與塔的數值同性質——現在只有 `orc_grunt` 一種敵人，真正的配置要等敵種補齊。第一章規格說潮汐在第 5 波轉，所以至少要 5 波；B4 做 **8 波**。

## 5. 提前呼叫下一波

新增意圖 `KIND_CALL_NEXT_WAVE`，走與建塔完全一樣的路：HUD 按鈕發 signal → `battle_scene` 翻成 `InputAction` → `InteractionController` → 意圖佇列 → `BattleSim` 路由。**新增的文法只有一個 kind**，B2 建立的那條路照樣覆蓋。

- 獎勵 = `floori(剩餘倒數秒數 × call_bonus_per_second)`，比率放資料裡
- 倒數已歸零、或正在生成中呼叫：**靜默忽略，沒有獎勵也沒有懲罰**（沿用 B1 起的分野——時機性的失敗靜默，資料錯誤才 `push_error`）
- 所有波次都生成完畢後呼叫：同樣靜默忽略

## 6. 通關判定讓模擬自己停下來

`WorldState.battle_finished` 在 tick 尾端判定：**所有波次都已生成完畢，且場上沒有活著的敵人。**

波次的執行期狀態（目前第幾波、倒數剩多少、各群組還要生幾隻）集中在一個 `WaveState` 物件裡，由 `WorldState` 持有一份——與 `grid`、`projectile_system` 同一個模式。不散在 `WorldState` 的欄位裡，是因為那些狀態只有 `WaveSystem` 會讀寫，攤平只會讓 `WorldState` 更難一眼看完。

一旦為真，`BattleSim.advance()` 直接回傳 0——**模擬自己停住，不需要 UI 去暫停它。**

這比讓結算面板去寫 `sim.paused` 好：那會是第二條改變模擬狀態的路，而 B3a 花了整個里程碑確保只有一條。順帶也自動滿足 B3a 留下的那條約束——「第一個模態對話框開啟時必須一併暫停模擬」，這裡模擬本來就停了。

「再來一次」用 `get_tree().reload_current_scene()`，整局重置。

## 7. 貨幣：欄位名不改，顯示名改

第一章規格 §4.5 定的單一資源是**銀**，`icon_silver` 圖示也已經畫好。

- `hud.gold_format` 的譯文從「金幣 %d」改為「銀 %d」（英文 `Silver %d`）
- **欄位名 `gold` 與 JSON 的 `starting_gold` 維持不變**

理由：`gold` 的語意沒有變（就是那唯一一種資源），變的只是它在畫面上叫什麼。塔防程式裡用 `gold` 泛指貨幣是慣例，而把 `gold`、`starting_gold` 與十幾個測試檔一起改名，換到的只有命名偏好。

**這個落差是刻意的**，寫在這裡免得下一個人以為是漏改。與 `lives` 的差別在於：`lives` 是語意變了（歸零不再是失敗），`gold` 只是顯示名變了。

## 8. HUD 與結算面板

### 8.1 HUD 新增

- 波次進度：第 N / 共 M 波
- 下一波倒數（生成中時顯示「進行中」）
- 呼叫下一波的按鈕，倒數中才可按

沿用 B3a 的規則：只在值改變時才寫 `Label.text`；`ui/` 只發 signal，由 `battle_scene` 翻成 `InputAction`。

### 8.2 結算面板

`ui/` 的新場景，模態，通關時出現：

- 三顆星的位置，第三顆恆為未達成
- 「撐過 8 波」「救到 14 / 20 人」
- 一顆「再來一次」

面板本身不需要暫停任何東西——模擬已經自己停了（§6）。

## 9. 測試策略

### 9.1 自動化

`WaveSystem` 整個可 headless 測試，這是這個里程碑最大的好處：波次推進、倒數、提前呼叫的獎勵、生成節奏、通關判定，全部是純邏輯。

| 測試 | 抓什麼 |
|---|---|
| 倒數與波次推進 | 第一波要等 `delay` 才開始；一波生成完才開始下一波的倒數；`interval` 決定生成節奏 |
| 群組錯開 | `start_delay` 有效，且同一波的多個群組各自獨立 |
| **提前呼叫的獎勵與剩餘秒數相符** | 與 B3b 的退款一致性同類：顯示與實付漂移是玩家會發現、測試不會的錯 |
| 呼叫的時機限制 | 生成中呼叫、全部生成完後呼叫，都靜默忽略且不給獎勵 |
| **通關判定不得在最後一隻敵人還活著時成立** | 最容易寫錯、而且畫面上看起來很像對的 |
| 通關後模擬停住 | `advance()` 回傳 0，且世界狀態不再改變 |
| 敵人建構只有一條路徑 | `DataRegistry.make_enemy` 與 `WaveSystem` 生出來的敵人欄位完全一致 |
| 資料完整性 | 每個 group 的 `enemy_id` 存在、`path_id` 存在於關卡、`count` 與 `interval` 為正、波數 ≥ 1 |

第五條要特別設計成有鑑別力：**一個在 `_remove_dead()` 之前判定的實作會通過大部分測試**，因為多數 tick 裡最後一隻敵人早就死了。測試要造出「這一 tick 敵人剛好被打死」的情境。

### 9.2 人工驗收

UI 與畫面不做自動化（`CLAUDE.md`）。跑 `godot --path .`：

1. 開局有準備時間，HUD 顯示第 1/8 波與倒數
2. 倒數歸零 → 敵人依 `interval` 一隻隻出來
3. 倒數中按呼叫 → 立刻開始，銀增加，增加量與按下時的剩餘秒數相符
4. 生成中按呼叫 → 沒有反應，銀不變
5. 一波生成完 → 倒數重新開始，波次進度前進
6. 敵人走到終點 → **平民數減少**（不是「生命」）
7. HUD 的資源顯示是「銀」不是「金幣」
8. 撐過第 8 波且場上清空 → **結算面板出現、模擬停住**（敵人與投射物不再動）
9. 面板顯示星等與「救到 N / 20 人」，第三顆星恆為未達成
10. 按「再來一次」→ 整局重置，回到第 1/8 波
11. 暫停與倍速仍然有效，且**倒數與生成都跟著暫停與倍速**

第 11 項是 B3a 那個修正的回歸驗收——生成現在住在 tick 裡，本來就該跟著。
