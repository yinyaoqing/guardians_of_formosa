## 0. 這份文件記錄什麼

第一章 33 類資產各出 2 張，跑了兩輪（純文字 prompt，SDXL Base 1.0，無參考圖、無 LoRA）。

**兩輪都沒有產出可用的單位貼圖。** 這份文件記錄失敗的形狀，因為失敗的形狀決定 A2 之前該補什麼。

美術聖經 §8 已訂「**A2 是閘門：母本集確立前不量產**」。這兩輪不是量產，是把閘門前該知道的事一次問完。

## 1. 兩輪的差異

| | 第一輪 | 第二輪 |
|---|---|---|
| 風格描述 | 膠彩顆粒、色層堆疊、粗筆觸（美術聖經 §4.1 原文） | 簡單卡通化：乾淨簡化形狀、大面積平塗、每色至多兩階明暗 |

| 內容正確性 | 差 | **一樣差，但換了一種錯法** |

第二輪的風格改動來自使用者指示。它有效——**風格軸線的問題，靠改 prompt 是可以解決的**。

## 2. 核心發現：內容錯誤不是 prompt 問題

**SDXL Base 1.0 沒有 17 世紀明鄭、西拉雅、亞洲 VOC 服飾的知識。**

缺乏知識時，它退回一個泛用的「前現代非歐洲士兵」先驗。而這個先驗的落點**會隨其他措辭漂移**：

| | 第一輪落點 | 第二輪落點 |
|---|---|---|
| 西拉雅鏢手 | 日本浪人（和服、木屐、假日文落款） | 穿長袍的中亞人 |
| 西拉雅頭目 | — | 綠袍光頭僧侶。**藤杖完全消失** |
| 漢人壯丁 | 日本浪人 | 中亞武士 |
| 鐵人軍 | — | **歐洲全身板甲騎士**（§3.2 明列負面詞） |
| 藤牌兵 | — | 青銅雕像／波斯武士 |
| 陳澤 | — | 拜占庭將領 |

第一輪加了 `japanese, kimono, ronin, ukiyo-e, samurai` 等負面詞後，日本消失了——**但換成波斯，不是換成明鄭**。

**結論：負面詞能趕走錯的答案，叫不出模型沒有的答案。** 繼續加負面詞只會讓落點在錯誤空間裡遊走。

§3.3 的藤杖（1636 年地方會議制度的權力信物，規格稱為「全章最重要的單一道具」）在兩輪中一次都沒有出現過。這是最能說明問題的單一事實。

## 4. 由此得到的三個決定

### 4.1 ~~圖示不要用 AI 生成~~（已失效，見 §9.2）

> **2026-09-05 修正：本節結論基於 SDXL 的觀察，已因換模型而失效。** FLUX.2 的圖示 12/12 成立。原文保留於下，作為「把模型能力的限制寫成永久產線決策」的反例。

12 張圖示全滅，且失敗模式一致——擴散模型會把「一個簡單符號」理解成「一整片裝飾」。

圖示是簡單幾何形狀，直接畫或用程式產出又快又保證一致。這與後處理管線（美術聖經 §5.3、精緻度規格 §3）「AI 畫不穩的事交給程式做」是同一個判斷。**把 icon 類從資產清單的 AI 產線移除。**

### 4.2 單位必須走參考圖條件生成

美術聖經 §2 對策第 2 點原文：「之後一律用參考圖條件生成，不用純文字 prompt。**文字 prompt 的變異性是風格漂移的主因**。」

兩輪實測證實了這句話，而且比規格寫的更嚴重——純文字 prompt 不只造成風格漂移，**還造成內容錯誤**。

A0 已裝好 IP-Adapter，工作流見 `art/workflows/a1_styled_ipadapter.api.json`。缺的是參考圖。

參考圖有兩種來源，**應該分開處理**：

- **風格參考**：可用本輪產出的場景與聚落（見 `art_src/02_selected/`）。這些是模型自己畫得對的東西，拿來鎖風格是安全的。
- **內容參考**：**AI 產不出來的服飾必須從史料圖像來**。美術聖經 §6 已列出 Vingboons 大員鳥瞰圖系列、1636 年《大員港市鳥瞰圖》等。西拉雅的部分還需要《東番記》相關圖像與 VOC 檔案插圖。

**這是一項需要人工蒐集的前置工作，不是能靠腳本解決的。** 沒有這批參考圖，單位資產做不出來。

### 4.3 姿勢與構圖用 ControlNet，不要靠 prompt

設定表崩壞（轉面圖、道具展開圖、假文字標註）在兩輪中都出現，加負面詞壓不掉。A0 已裝 ControlNet Union promax，涵蓋 openpose 與 depth。

美術聖經 §7.4 的 Blender 粗模流程本來就要用它——**把它提前到單張定稿階段用**，構圖就不再由模型自由發揮。

## 7. 第二階段實測：ControlNet、LoRA、參考圖

2026-09-04 依 §4 的三個決定實作並實測，結果如下。

### 7.1 ControlNet 姿勢控制：有效，且是決定性的

骨架圖由 `art/scripts/make_poses.py` 程式產生（8 組姿勢，OpenPose BODY_18），不從別的圖抽。

**兩輪純文字 prompt 都壓不掉的設定表崩壞，加上 ControlNet 後完全消失。** 六張測試全部是單人、站姿、全身入鏡、置中、素底。這是本階段唯一決定性的成功。

限制要說清楚：OpenPose 只有五官關鍵點、沒有顱頂，**它鎖的是四肢位置與構圖，頭身比只能間接影響**。關節座標依 4 頭身佈置，但實際頭身仍需人工驗收。

### 7.2 社群風格 LoRA：授權可用，但效益沒有出現

下載 `artificialguybr/StoryBookRedmond` 與 `CuteCartoonRedmond-V2`，皆為 CreativeML OpenRAIL-M，可商用。

第一次測試三個變體（兩個 LoRA + 無 LoRA）產出幾乎相同——**原因是我用了 `LoraLoaderModelOnly`，它只掛 model 不接 CLIP，觸發詞寫了等於沒寫**。改用 `LoraLoader`（model + clip）並把強度提到 0.9 後重測，**三排仍然幾乎一模一樣**。

**結論：在這條管線裡，換社群風格模型沒有帶來可測量的改變。** ControlNet 強度 0.85 加上很長的具體 prompt 已經主導生成，LoRA 的風格訊號被淹沒。模型已安裝、授權已查證，但不要期待它解決問題。

### 7.3 IP-Adapter + 史料參考圖：內容問題解決了

這是本專案第一次產出服飾正確的單位。

| 參考圖 | 產出 |
|---|---|
| 《出警入蹕圖》明代布面甲 | 笠形盔、明制號衣、東亞面孔——前兩輪拿到的全是波斯與日本人 |
| Jacob de Gheyn《Wapenhandelinghe》(1607) | 寬邊帽、及膝馬褲、斜掛彈藥帶、手持火繩槍，正是規格 §3.1 的描述 |

**§2 的診斷得到證實**：模型缺的是知識，不是提示詞。餵圖就有，不餵就沒有。

### 7.4 但參考圖會把媒介一起搬過來

明代參考讓產出變成絹本設色（還多出一匹馬，骨架被蓋過）；de Gheyn 參考讓產出變成 19 世紀手工上色服飾圖鑑——**正是前兩輪花力氣消滅的那個失敗模式**。

把 IP-Adapter 權重從 0.60 一路降到 0.30、`end_at` 降到 0.30，圖鑑風仍在。

**根因：史料參考圖本身就是圖鑑與繪畫。餵圖鑑又要求卡通，是矛盾的要求。**

### 7.5 兩階段分離：階段 A 成立，階段 B 不成立

```
階段 A  a1_unit_ref_pose.api.json   IP-Adapter（史料參考）+ ControlNet（骨架）
階段 B  a1_stage_b_restyle.api.json 把畫風換成卡通
```

**修正：本節初版曾記錄「階段 B 實測有效，denoise 0.50 最佳」。該結論已被推翻**——當時只比對了縮圖觀感，沒有量測。實際逐像素比對後，階段 A 與 B 的平均差只有 7–22（滿分 255），媒介完全沒換掉。

#### 階段 A：成立，但有前提

三個資產（鄭軍銃卒、西拉雅鏢手、鐵人軍）實測：

| 前提 | 結果 |
|---|---|
| 參考圖是**單一孤立人物**（1652 年福爾摩沙人） | ✅ 裸上身、圍腰、赤足、修長——完全符合章節規格 §3.3。**本專案第一次產出服飾正確的單位** |
| 參考圖是**多人長卷**（出警入蹕圖騎兵） | ❌ 馬、旗、多人物、絹本底一起被搬進來，ControlNet 骨架被蓋過 |
| 長卷**裁成單一軀幹**後 | 🔶 馬消失、單人全身、姿勢正確；但畫風垮成中世紀泥金手抄本 |

**規律：IP-Adapter 搬的是整張參考圖，不只是你想要的那個部分。參考圖必須是單一孤立人物。**

骨架的量體參數也驗證有效：鐵人那排明顯比銃卒寬而方（`shoulder 1.40 / stance 1.60 / crouch 0.45 / line 20`）。

#### 階段 B：五種機制全部失敗

| 版本 | 機制 | 結果 |
|---|---|---|
| 1 | img2img denoise 0.50 | 像素平均差 7–22，媒介沒換掉。低 denoise 保住服飾的同時也保住畫風，這兩件事在 img2img 裡是綁在一起的 |
| 2 | + Canny + denoise 0.80 | 更糟。Canny 邊緣抽自手抄本風的圖，把該畫風自己的裝飾線條複製過來——ControlNet 變成在**強化**畫風 |
| 3 | + IP-Adapter 餵人物風格參考 | 產出全部長出參考圖那個人的白鬍子與靴子 |
| 4 | + IP-Adapter 餵聚落地形圖 | **人物直接變成干欄式茅屋** |
| 5 | + 風格 LoRA 1.0 + denoise 0.62 | 無變化 |

另在階段 A 掃描 IP-Adapter 參數（weight 0.45／0.60／0.75 × end_at 0.25／0.35／0.45），**九種組合全部仍是手抄本風**。

#### 由此得到的結論

**媒介汙染無法在下游移除，只能在上游避免。**

- 版本 3 與 4 揭示一條通則：**IP-Adapter 搬的是內容，不只是風格**。用任何圖當「風格參考」，那張圖的主體都會被複製進來。
- 版本 2 揭示第二條：**任何從已汙染影像抽出的結構條件（邊緣、線稿），都會連同該影像的畫風一起複製**。
- 降低 IP-Adapter 權重與生效區間沒有用，因為手抄本風不是參考圖強度造成的，而是**低資訊量的裁切**（111×148 放大六倍）讓模型退回「平面裝飾性人物」的先驗。

**因此鄭軍與鐵人的瓶頸不是參數，是參考圖品質。** 需要的是一張解析度足夠的**明代單人步兵**圖像——而 Commons 的《出警入蹕圖》全是騎兵，這正是 `reference_images.json` 的 `_gaps` 已記錄的缺口。西拉雅之所以成功，正因為它剛好有一張合格的單人參考。

### 7.6 剪影檢查：現有陣容不及格

`art/scripts/silhouette.py` 實作了精緻度規格 §4 的第 ② 步。

對第二輪的 34 張單位執行，**38 對的剪影相似度超過 0.93**——畫面上幾乎每個單位都是「一個人拿著一根棍子」，128px 下完全分不出來。

只有三個剪影真的成立：鐵人的厚重方塊、藤牌兵的圓盾團塊、揆一的寬邊帽。

章節規格 §3.4 已為各陣營定義剪影特徵（笠形盔的三角、鐵人的方塊、鏢手的長鏢斜線），**但那是設計目標，現況離它很遠**。剪影檢查應在上色前跑，不是事後。

### 7.7 史料參考圖蒐集

`art/manifest/reference_images.json` + `art/scripts/fetch_refs.py`，全部取自 Wikimedia Commons 的公有領域／CC0 素材，出處與授權寫入 `art_src/refs/_provenance.json`。**參考圖只用於生成條件，不進遊戲。**

一個意外收穫：`File:Landdag.jpg`——地方會議正是頒發藤杖的場合，原本被列為缺口的 §3.3 關鍵道具因此有了間接參考。

實際取得 14/19。仍存在的缺口見清單的 `_gaps`：

- **內容缺口**：鐵人軍的「全身鐵甲＋鐵面罩＋赤足」組合、長鏢實物、17 世紀台灣漢人移民服飾，Commons 上根本沒有，需另尋來源。
- **技術缺口**：5 張的 Commons 縮圖服務算不出來，只能抓原檔，而原檔下載被 IP 層級的 429 擋住（curl 亦然）。皆為次要圖，四個群組都已有可用參考。

抓圖過程本身有兩個值得記下的坑。其一，**要求的縮圖寬度若大於等於原圖寬度，Commons 不會給 `/thumb/` 路徑，只回傳原檔 URL**——而原檔下載正是被限流最嚴的一種。修正為依原圖尺寸往下取一階標準寬度後，原本卡住的 8 張補回 3 張。其二，**必須用標準尺寸**（120/180/240/320/400/500/640/800/1024/1280/2560），指定 1600 這種值會強迫伺服器即時算圖，同樣招來 429。

**這些圖像本身帶有殖民視線**（美術聖經 §0），取其服飾與器物形制，不取其取景與姿態。

### 7.8 解析度

單位生成從 832×1216 降到 768×1024。最終只有 128px，高解析度是浪費；省下的時間換更多候選張數，對「10 選 1」比解析度重要。

## 8. 換模型：FLUX.2 Klein 4B（決定性突破）

§2 的診斷是「模型缺的是知識，不是提示詞」。既然如此，換一個知道這些知識的模型應該直接解決問題——2026-09-05 實測證實了。

### 8.1 結果

同樣的清單、同樣的 prompt 組裝、**沒有參考圖、沒有 ControlNet、沒有 LoRA**，純文字生成：

| 資產 | SDXL（兩輪 + 兩階段共 70+ 張） | FLUX.2 Klein 4B（2 張） |
|---|---|---|
| 鄭軍銃卒 | 波斯武士／日本浪人／中世紀手抄本 | ✅ 笠形盔、硃砂號衣配盤扣、**赤足**、東亞面孔、束髮、火繩槍 |
| 西拉雅鏢手 | 和服木屐／中亞長袍／綠袍僧侶 | ✅ 裸上身、獸皮圍腰、赤足、長鏢過肩且明顯長於身高一半、束髮、耳飾與腕飾 |
| 鐵人軍 | 歐洲全身板甲騎士 | 🔶 布面甲、鐵面罩、藤牌在背、赤足、厚重量體；但盔形偏歐洲，缺過肩斬馬刀 |

**單位可用率：SDXL 0/66 → FLUX.2 5/6。**

§3.2 特別強調「鐵人的赤足是關鍵設計點，不要讓 AI 幫它加靴子」——SDXL 兩輪都加了靴子，FLUX.2 六張全部赤足。

### 8.4 三個踩過的坑

1. **klein 的文字編碼器是 Qwen3-VL，不是 Mistral。** Mistral Small 那顆（11.4 GB）是 FLUX.2 **dev** 用的。依據為 `comfy/sd.py:1915` 的註解「Flux2 Klein reuses the Qwen3-VL LM」。抓錯會多下載 8 GB 且無法載入。
2. **FLUX 是 guidance-distilled**：KSampler 的 `cfg` 必須固定 1.0，強度改由 `FluxGuidance` 節點控制；latent 要用 `EmptyFlux2LatentImage` 而非 `EmptyLatentImage`（通道數不同）。
3. **VAE 有 dev 版與 klein 版兩顆同名檔案**，差 2264 bytes。抓錯不會報錯，只會讓輸出色彩失準。下載腳本的大小驗證抓出了這件事。

### 8.5 仍未解決的

- **鐵人的斬馬刀與盔形**仍需修正，可用局部重繪。
- **背景是灰底不是透明**，由 A4 後處理管線去背。
- **藤杖**尚未測試，仍是最冷僻的道具。

### 8.6 對規格的影響

美術聖經 §7.3 原訂「不使用 Flux」，理由是 `[dev]` 非商用、`[schnell]` 品質不足。**FLUX.2 Klein 4B 兩個理由都不成立**：Apache 2.0 可商用，且品質遠勝 SDXL。該條已修訂。

## 11. 陣營識別色與 A4 後處理管線

### 11.1 藤黃寫在句尾不會被畫出來

美術聖經 §2.2 要求玩家方一律帶一塊藤黃 `#E0A93B`、敵方一律沒有。清單的 `subject` 其實**早就寫了**（「a gamboge yellow armband」等），但九個玩家方資產的產出全都沒有。

原因是位置：藤黃埋在長句尾端會被稀釋。改成獨立段落 `FACTION MARK: one large unmistakable patch of bright gamboge yellow #E0A93B — the single most saturated element in the whole image` 之後全部出現。

**這已經是第三次遇到同一個規律**：A0 §6.1 的段落順序、§10.2 的姿勢、以及本節的識別色——**重要的東西必須獨立成段，塞進長句尾端等於沒寫。**

### 11.2 解掉一個規格衝突

章節與美術規格互相牴觸：§3.2 給藤牌兵「藤黃盾面」、陳澤「金」，而 §2.2 說敵人一律沒有藤黃。

**依 §2.2 處理**（使用者確認）。藤黃在本作不是裝飾色而是陣營標記，一旦敵方也有，「玩家一眼看得出自己的人沒變」就失效——那是 §0.2 決定一的視覺載體。藤牌改自然藤色（近沙洲黃），陳澤的「金」取青銅金。美術聖經 §2.2 已補上「本規則凌駕 §3 各表的逐一單位配色」。

### 11.3 色票的膚色例外已入規格

§2.1 原文「任何資產不得引入色票外的色相」，但後處理的色票量化會把人臉映射成赭紅或沙洲黃——那不是風格化，是壞掉。

已在 §2.1 補上四階膚色作為**唯一的例外**。四階的分野同時承擔章節規格 §2.5 與 §3.3 的敘事要求：城內 547 名奴隸不是背景，把 VOC 畫成純歐洲人前哨是美化殖民地，膚色分階是這件事在美術上的最低限度落實。

### 11.4 A4 後處理管線（①②④）

`art/scripts/postprocess.py`。33 個資產 13 秒。

| 精緻度規格 §3 的步驟 | 狀態 |
|---|---|
| ① 去背與裁切 | ✅ |
| ② 色票量化 | ✅ |
| ③ 描邊統一 | ✅ 見 §12 |
| ④ 縮放至 128 並檢查剪影 | ✅（剪影檢查在 `silhouette.py`） |
| ⑤ 打包 Sprite Atlas | ❌ 未實作 |

**去背不能用「整張圖比對背景色」**——那會把單位身上同色的部分一起挖掉（灰袍、灰甲）。改用從四邊泛洪填充，只吃與畫布邊緣連通的像素，內部同色區塊保留。實測乾淨：弓的內側負空間正確透明、人物無破洞。

### 11.5 三個踩到的坑

1. **場景不該去背。** 地形貼片是滿版背景，泛洪會把邊角吃掉。已對 `scene` 類跳過。
2. **地面陰影不可烘進資產。** 精緻度規格 L1 明訂接觸陰影是引擎端共用的橢圓貼圖、隨 y 座標調整長寬濃度；烘進去會變兩層且無法動態調整。已在 framing 與負面詞要求不畫。
   順帶釐清：**L2 的「短而硬的投影」指的是角色身上的明暗，不是地面橢圓**，兩者不衝突。
3. **我把 prompt 寫成自相矛盾。** building／prop 的構圖原本有「sitting on its own small patch of ground」，加防呆時又接上「no patch of ground」，同一句前後打架，所以道具類的地面清不掉。移除前半句後才生效。

## 12. 描邊統一與色票一致性檢查

### 12.1 規格內部的張力，以及怎麼解

- 美術聖經 §1.1 要「**彩色描邊，粗細有變化，帶手繪抖動**」
- 精緻度規格 §3 要「**程式加，保證粗細與顏色一致**」

粗細一致與粗細有變化是相反的要求。解讀：**§1.1 講的是角色內部的線描**（那是生成模型畫的，本來就有變化，管線不動它）；**§3 要統一的是外輪廓**——讓所有資產在任何地形上讀起來是同一套。兩者不衝突。

故 `outline()` 只加外緣。顏色不是單一黑色，而是取相鄰像素的暗化色後吸附到焦茶／深赭／墨綠三色——實測膚色邊緣落在深赭、綠褲邊緣落在墨綠、藍衣邊緣落在焦茶。這保住了 §1.1 與 Kingdom Rush 區隔的第一項（粗黑均勻描邊）。

### 12.2 ③ 與 ④ 的順序刻意與規格相反

規格寫「③ 描邊 → ④ 縮放」。但描邊若加在縮放前，1024px 上的 3px 縮到 128px 只剩 0.4px，**「保證粗細一致」這個唯一目的就沒了**。故本管線先縮放再描邊，線寬以最終像素為準。

### 12.3 色票一致性檢查抓出了管線自己的 bug

§3「建議的自動檢查」第一項是色票一致性。實作後**第一次執行就 33/33 全部失敗**。

失敗值很說明問題：`#E8DBC5` vs 色票 `#E8DCC6`、`#6A472E` vs 膚色 `#6B472E`、`#2C5571` vs `#2C5470`——**每個通道差 1–2**。

原因是我把管線順序寫成「量化 → 縮放」，而 LANCZOS 縮放會插值，把量化好的顏色重新混出中間色。**縮放之後量化就失效了。** 改成「縮放 → 量化 → 描邊」後 33/33 通過，順帶讓量化在 128px 而非 1024px 上跑，快一個數量級。

**這正是規格 §3 那句話的實例**：「在 AI 協作下，只有能自動驗證與自動執行的東西才不會腐化。」量化的程式碼一直在跑、看起來也沒報錯，但它做的事被下一步抵銷了——沒有那支檢查，這個 bug 會一路帶到 `game/assets/`。

## 13. 色票檢查接進 GdUnit4

### 13.1 色票抽成共用資料

`data/art_palette.json`（依 CLAUDE.md「遊戲資料一律 JSON，置於 `data/`」）。

### 13.2 三個測試

| 測試 | 目的 |
|---|---|
| `test_palette_json_is_loaded` | 色票本身若空掉，其餘測試會全部「通過」而毫無意義 |
| `test_all_assets_use_only_palette_colors` | 掃描 `game/assets/` 的 PNG |
| `test_detects_deliberately_injected_off_palette_color` | **美術聖經 §8 的 A4 完成判準**：「測試能抓出刻意混入的色票外資產」 |

第一與第三個測試是**針對測試本身的測試**。沒有它們，第二個測試在資產目錄為空時也會通過——看起來過了，其實什麼都沒驗。這種「空過」在美術資產尚未進 `game/assets/` 的現階段特別危險。

灰盒佔位圖（`placeholder_*`）豁免。精緻度規格 §4 訂的開發順序是灰盒優先，佔位圖刻意不是美術，拿色票檢查它沒有意義。豁免前綴寫在 JSON 裡而非程式碼裡。
